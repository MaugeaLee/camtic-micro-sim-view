# 렌더 뷰어 (이 레포 런타임)

이 레포에 처음 생긴 실행 코드다. `theuniversepark/meta-factory`의 **개발 구조**(import map · 조립 루트 · 상태/뷰 분리 · 정적 서버 · 헤드리스 테스트)만 옮겼고, 그쪽 기능(에이전트·CCTV·AAS·5G·FAC)과 뷰포트 내용은 가져오지 않았다.

시뮬 런타임이 아니다. 셀 GLB를 보여 주는 뷰어다. 장 A/B/C 어디에도 아직 붙지 않았다(`ARCHITECTURE.md` §7).

## 실행

```
npm start          → .env 의 HOST:PORT (예제 127.0.0.1:8790)
npm test           → tests/*.mjs 헤드리스
/api/docs          → Swagger UI
?assets=1          → 셀 GLB 자동 로드 (기본 꺼짐)
Admin 버튼         → 타이틀 오른쪽. 짓기(집기·놓기) 켜고 끔. `?build=1` 이면 켠 채로 시작
좌·우 패널         → 가장자리 버튼으로 해당 쪽으로 접기. 남은 탭을 누르면 다시 연다
?scenario=faults   → 시나리오(기본 faults · supply · none). 상단 드롭다운으로도 바꿈
?amr=2             → 도어트림 AMR 대수 1~10 (기본 = 시나리오 값 4)
?play=1            → 재생 상태로 시작
?warp=130          → 점검용. 시뮬을 그만큼 미리 진행
?focus=SORT        → 점검용. 셀 id 또는 AMR id(AMR-01)에 카메라 포커스
__viewer.loadAssets()   콘솔에서 수동 로드
```

의존성 설치 없음. Three r186 은 `vendor/three/`에 필요한 파일만 있다.

규칙:

- 레이어끼리 서로 import 하지 않는다. `core`만 예외로 아무나 읽는다. 잇는 건 `main.js`.
- 이벤트 버스 없음. `state.emit()`이 쌓고 `main`이 프레임마다 한 번 `drainEvents()`해서 소비자에게 넘긴다. UI는 `state.logs`를 폴링.
- 상태 변경은 `ViewerState` 메서드로만. 뷰·UI는 콜백으로 요청.

## 루프

```
frame():  rdt = min(Δ, 0.1)
          state.advance(rdt)      배속 × rdt 를 0.1 s 단위로 쪼개 step (시나리오가 있으면 plant.step)
          hub.tick(state)         10 s(시뮬)마다 스냅샷 (AMR 위치 포함)
          events = state.drainEvents()
          view.update · fleetView.update(rdt, state, events)
          rigView.update(셀, plant.work[셀].view()) · partsView.update(plant.partPoses())
          select/follow 이벤트 → rig.focus · rig.follow → rig.update(rdt)
          stage.render()
          ui.update(state)        0.25 s(벽시계)마다
```

부트: `createStage` → 뷰/허브/UI 생성 → `start()`(상태 새로 만들고 `view.setup`) → (옵션) 에셋 로드 → `__ENV.api.status` → `frame()`.

## 좌표·에셋

- 1 = 1 m, Y-up. glTF 규약 그대로.
- 셀 id = STEP 최상위 조립품(`PRESS` `SCREW` `SORT`). 시뮬 셀 ID(SORT…)·OCS A-3-n 과 맞추지 않는다. 견적 코드(S/P/K/A)↔그룹은 `context/08-precision-y1-equip.md`. `PRESS`는 압입 체결구역이다.
- GLB 디스크·URL은 `.env`의 `ASSET_DIR` · `ASSET_URL`. 쓰는 자리는 `LAYOUT_FILE`(기본 `data/layout.json`). 없거나 깨지면 `src/layout.default.json`만 읽는다. PUT은 `LAYOUT_FILE`에만 쓰고 기본 파일은 덮지 않는다. 메인은 GET `/api/layout`만 읽고, Admin 모드에서 셀·완료품·창고 집기·놓기와 AMR 경로 편집을 한다. 보기 화면은 2초마다 GET해서 따라간다.
- 필드(`field-def.js`): 76 × 30 m, 벽 높이 8 m, 뒷벽·좌우 벽, 앞면 열림. **실측 아님** — 셀 3개 + 서쪽 완료품 구역 + 동쪽 반출·부품 통로가 들어갈 크기로 잡은 가정이다. 바닥 텍스처는 캔버스로 생성(고정 시드, 한 장 4 m · 격자 1 m)하고 이미지 파일은 없다.

시뮬을 돌리지 않는다. 정적 + 읽기 전용(레이아웃 PUT만 예외, 루프백). 리슨·에셋은 `.env`. API 경로는 `server/env.mjs`의 `API` 상수. 버전은 `package.json`.

## 관절 추정 (`js/assets/rig.js`)

이 셀 GLB에는 `J1`–`J6` 피벗·`extras.axis`·스키·클립이 없다. 메시는 조립품 아래 **형제**이고 TRS는 거의 identity다. 루트 Object3D를 돌리면 강체 요(yaw)가 되어 기구학이 아니다.

참조 레포(meta-factory)는 빈 피벗 체인 아래 링크 메시를 두고 `pose()`만 한다. 이쪽은 그 피벗을 **로드 시 형상으로 만들고**, 같은 구조로 조립한다. 부품 이름표·로봇별 JSON·사람이 고른 축은 쓰지 않는다. `TUNE`은 전역 임계값 한 벌이다.

대상 목록도 이름(`R\d+`)이 아니라 `inferRig().robot === true` 인 그룹이다. PRESS·SCREW·SORT를 열면 검출된 팔을 **전부** 같은 규칙으로 묶고 같이 재생한다. `BENCH.*.name`은 카메라 포커스 기본값일 뿐 관절 매핑이 아니다.

### 하지 말 것

- 루트 그룹을 통째로 회전
- `ShoulderHousing → J2` 같은 이름 규칙
- 로봇마다 다른 축·원점 표
- GLB에 없는 6축을 있는 것처럼 쓰기

### 절차

1. 씬을 순회한다. 자식이 4개 이상인 그룹마다, 자식 메시 점을 월드로 모아(최대 4000점) `inferRig(parts, { up: [0,1,0] })`에 넣는다. 부품 수 3 미만 또는 120 초과는 빈 결과.
2. 부품마다 AABB와 `roundAxis`(회전 대칭)를 구한다.
3. AABB 틈 ≤ `max(0.003, 전체대각선 × 0.01)` 이면 맞닿은 것으로 잇는다. 떨어진 덩어리는 최근접 틈 + 같은 허용치 안의 쌍을 한꺼번에 잇는다.
4. `up` 방향으로 가장 낮은 부품을 고정 베이스(루트)로 둔다.
5. 베이스에서 멀어지는 순으로 대칭 부품을 관절 후보로 본다. 직렬 깊이 ≥ 3 이면 로봇.

### 하우징·축 (`roundAxis`)

회전 대칭 부품(원판·짧은 원통)을 관절 하우징으로 본다. 자기 축으로 돌아도 모양이 같아서, 하우징이 관절 앞·뒤 어느 링크에 붙어도 결과가 같다. 대칭축 = 회전축, 중심 = 원점.

- 점 공분산 고유값 3개. 두 축 분산이 비슷하고(`≥ 0.8`) 나머지 한 축이 뚜렷하면(`≤ 0.75`) 그 한 축이 후보.
- 세 분산이 비슷하면(길이 ≈ 지름 × 0.7 원통) 고유벡터와 ±X/Y/Z를 돌려 보고, 바깥 둘레 점 비율이 가장 큰 축을 쓴다.
- 바깥 둘레(반지름의 90% 이상) 점이 16칸 중 9칸 이상을 채워야 원이다. 사각 판·모서리만 있는 형상은 탈락.
- 축 방향 길이 > 지름 × 1.6 이면 링크·롤러·레일이다. 하우징이 아니다.
- 앞선 관절과 축 내적 ≥ 0.97 이고 축–점 거리 ≤ 전체대각선 × 0.04 이면 **새 관절이 아니라** 그 관절의 베어링·캡. 같은 링크에 묶는다.

### 관절이 아닌 접촉 (`isCut`)

관절이면 먼 쪽 덩어리가 몸통에 닿는 자리는 하우징 근처여야 한다. 닿는 점이 하우징 중심에서 `max(2.5 × 반지름, 3 × 틈허용)` 밖이면 후보를 버린다. 흡착 패드·컨베이어 롤러가 이 조건으로 빠진다.

### 조립·재생

추정한 관절마다 빈 그룹 `J1`… 을 원점에 두고, 링크 부품을 `attach`로 그 아래로 옮긴다. 축은 그룹 로컬로 변환해 `quaternion.setFromAxisAngle`에 쓴다. 가동 범위는 `±π`로만 두고, 재생 진폭은 `anim.js`의 `sin(t)` (대략 0.25–0.6 rad)다. 간섭 검사는 없다.

## 운동 종류 (`js/assets/movers.js`)

팔 추정(`inferRig`)을 레일·AMR·롤러에 다시 쓰지 않는다. 짧은 원통은 관절 하우징, 가로 짧은 원통 묶음은 바퀴, 가로 긴 원통은 롤러, 가로로 긴 가이드는 레일이다. 한 규칙으로 섞으면 패드·레일·바퀴가 가짜 팔 관절이 된다.

`classifyMover` 순서: 팔 → 바퀴 → 롤러 → 직교 → 레일. 조상 그룹이 자식과 같이 잡히면 자식만 남긴다. 부품 이름표·종류별 JSON은 쓰지 않는다.

| kind | 형상 | 동작 |
|---|---|---|
| `arm` | `inferRig().robot` | 내부 메시를 `J1`… 피벗 아래로. `jointWave` |
| `amr` | 가로 짧은 원통 3–8개, 반지름·높이 비슷. 큰 지그 상판+다리는 제외 | 차체 `travelWave`. 바퀴는 이동/반지름으로 자전 |
| `rollers` | 가로 긴 원통 4개 이상 | 제자리 `spinWave`. 베드 자체는 고정 |
| `gantry` | 문형 기둥 3–6 + 문 위 Z기둥 + 흡착 공구. Cross가 긴 Side 레일을 탐 | `gantryWave`: 캐리지(Cross+헤드)는 레일 방향, 흡착만 수직. Side·프레임 고정 |
| `track` | 가로 긴 AABB 가이드 2–4개, 길이 비슷, 나란히(경로 조각 제외) | 레일은 고정. 레일 위 팔 그룹을 축으로 슬라이드 |

재생은 검출된 대상 전부. `BENCH.*.name`·드롭다운은 카메라 포커스다. 메인 뷰는 이 판정으로 `amr` 그룹만 숨기고(공급 AMR 플릿으로 대체), 팔·롤러·직교 재생은 아직 안 붙인다.

합성 점군은 `tests/movers.mjs`. 실제 GLB에서 팔 15대가 그대로인지, 직교 2축이 `gantry`인지, MAIN JIG 도킹이 AMR로 안 움직이는지, 레일/롤러가 팔로 안 잡히는지를 같이 본다.

## 시나리오·ACS (`js/sim/scenario.js` `acs.js` `fleet.js` `route.js` `amrdata.js`)

**가정 흐름.** 확정 공정이 아니다. 도어트림 AMR이 원재료를 SORT 랙 뒤(`SORT:RAW`)에 하역하면 협동로봇이 랙에 올리고(버퍼 2), 분류된 키트를 북쪽 양팔 도크에서 다시 실어 SCREW(42 s)·PRESS(40 s) **서쪽** 셀 안 도크로 나른다. 공정 정의가 있으면 완료품은 빈 AMR 이 **동쪽** 도크에서 협동로봇에게 받아 완료품 적재 구역(OUT)으로 나른다. 셀은 키트 하나로 한 사이클 돈다. 재고 상한은 2다. 셀 상태: 키트 없음 IDLE · 작업 중 BUSY · 고장 DOWN. 기본 시나리오(`supply`)에는 고장이 없다. `faults`(점검용)만 540 s 주기로 PRESS→SORT→SCREW를 한 번씩 세운다.

**층 나눔.** `Plant`(scenario.js)는 셀 상태·키트·재고와 미션 요청만 한다. 운반은 전부 ACS(acs.js)다. ACS는 미션 큐·배차·경로 계획·예약을 맡고, AMR(fleet.js)은 받은 단계를 달리며 감지·양보만 한다.

**지도 데이터 (레이아웃 v2 `amr`).**

| 항목 | 내용 |
|---|---|
| `route.nodes` · `edges` | 필드 좌표 그래프. 양방향 간선은 진행 방향 오른쪽 차로(±0.7 m), `oneway`는 중심선. 꺾임은 마이터로 이음 |
| `homes` | 충전 자리(기본 도어트림 6 · 부품 3, 상한 10). 도어트림은 북쪽 통로 한 줄, 부품은 창고 `PARTS` 좌우. AMR이 처음부터 여기 서 있다. 루트를 등지고 서서 앞으로 들어오고 후진으로 나간다 |
| `cells.{id}` | 셀 로컬 `entry` · `stops`(마지막 = 도크) · `exit`(없으면 막다른 셀). 셀을 옮기·돌리면 같이 움직인다 |

기본 지점은 GLB에서 잰 자리다(`tests/glb.mjs`가 대조). PRESS·SCREW 투입 도크 = Roller_01 앞(서쪽), 완료품 반출 도크 = AMR_route 동쪽(x +1.83). SORT 대기 2칸 = AMR_waiting_2·3, 도크 = AMR_dual_pickup, 출구는 동쪽.

**예약 세 겹.**

| 예약 | 규칙 |
|---|---|
| 셀 잠금 | FIFO. 막다른 셀 1대, 통과 셀은 정차 칸 수. 접속점 앞 대기점(≥ 2 m)에서 줄, 4 m 앞에서 잡히면 서지 않고 들어감 |
| 정차 칸 | 다음 칸을 잡고 움직인 뒤 이전 칸을 놓는다. 도크는 마지막 1 m를 0.3 m/s로 들어가 셀 방향으로 정렬 |
| 교차 구역 | 셀 입구·출구가 루트에 붙는 자리마다 원(반경 1.8 m, 겹치면 합침) + 다른 플릿 루트와 만나는 자리(r 2.3 m, 공유). 몸체가 원에 들어가려면 그 구역을 잡아야 한다. 대기점은 구역 밖. 밖에 자리가 없으면(SORT 출구→PRESS 입구) 출발 전에 목적 셀 잠금부터 잡는다 |

**감지·양보.** micro-assembly `Mover.yieldTo`·`sense`를 남겼다: 차폭 안 전방 + 개인 간격 1.34 m, 마주침 → 낮은 우선순위가 비켜섬, 교차 막힘 → 낮은 쪽이 물러남, 선 차량 우회. 셀 잠금 안·같은 셀 줄·구역 대기 차 뒤에서는 우회 없이 기다린다. 15 s 교착 → 4 s 우선 통행은 안전망으로만 남겼다(테스트에서 0회). 운동: 0.3 rad 넘게 틀어지면 서서 돈다, 가감속 0.7 m/s², 빈 차 1.5 · 적재 1.1 · 후진 0.45 · 도크 0.3 m/s.

**견마 리커버리(가정, M-25–M-31).** 사족보행 한 대(`HOUND-01`)가 셀 앞·사이 통로를 지그재그로 순찰하다 실제 이상만 보고하고, 자체로 열 수 있으면 차체를 밀어 간격을 연다. 필드 끝·충전 자리 줄은 순찰에 쓰지 않는다. 이상 = 통로 겹침(차체 원 교차)·맞물림(서로 blockedOn)·장시간 끼임(blockT≥8 s). 도크·충전 자리 정박(`isDocked`: 핸드셰이크·셀 칸 대기·홈 대기)과 줄서기·하역 대기는 정상이라 `hound:event` 를 내지 않고, 정박한 차 앞에서도 서지 않는다. 출동하면 로그·emit 뒤 밀기(`hound:recover`, 같은 쌍 18 s 재출동 금지). AMR 레일에 묶지 않는다. 셀·창고 발자국은 통로 격자로 돌아가고, 움직이는 앞차에는 선다. 순찰 0.85 · 출동 1.15 m/s, 가감속. 셀 안 이상은 경계까지만 간다. 형상은 참조 레포 `quadruped.glb`. 시뮬 배우이지 하드웨어 OCS·PLC 순찰이 아니다. `?focus=HOUND-01`.

**배차.** 키트 수 + 곧 나올 키트(10 s 이내)만큼 최대 3건을 미션 큐에 넣는다. 놀고 있고 배터리 30 % 이상(충전 복귀했으면 85 %)인 차 중 가장 가까운 차. 하역 뒤 큐에 미션이 있으면 바로 이어 받는다. 경로 점검에 걸린 셀(도달 불가·접속선이 다른 셀을 지남·접속선 > 4 m)은 배차에서 뺀다.

**대수.** 기본 도어트림 6대 · 부품 3대, 상한 10대(`?amr=` 은 도어트림만). 충전 자리 수가 상한이다.

**SORT 분류 흐름 (M-19–M-21, 가정).** 부품 AMR이 창고에서 쌓인 라인 요청만큼(`supply.batch` 최대 4, 적재면 두 칸 × 2단) 싣고 SORT 투입 자리 `SORT:IN`(부품 루트의 셀 「SORT:IN」, 막다른 1칸)에 선다. 투입 이송기(`cells.SORT.feed.infeed`)가 위 칸부터 컨베이어 낙하점으로 옮기고, 마지막 토트를 들면 AMR은 다른 미션으로 간다. 컨베이어 위 토트는 스캔(`scan` 1.5 s) 뒤 목적 도크 → 레인을 정하고(`lanes[].to`), 제 레인 앞까지 가서 분기 이송기가 레인 롤러 시작으로, 레인 롤러가 끝까지 보낸다. 스캔 순간 `Supply.laneTrip` 이 레인 AMR 미션을 낸다: 부품 AMR이 SORT 셀의 그 레인 칸에 와서 서 있고, 내림 이송기가 적재면(`supply.top` 1.11 m — 그리기는 상부 모듈)에 놓으면 출발해 라인 팔레트로 간다. 레인 = 라인 쪽: A PRESS 북(L03·L04) · B PRESS 남(L01·L02) · C SCREW 북 · D SCREW 남. 레인 롤러 칸 3 ≥ 레인당 라인 2라서 분기가 컨베이어를 막지 않는다. 도어트림 AMR은 그대로 양팔이 직접 싣는다. 이송기는 GLB 갠트리 노드(이름은 `feed`)를 한 축 + 승강으로 움직이고 쉼 높이는 툴 하위 상자 밑면(`rigdata.js` `toolLow`). GLB 레인 위 고정 토트(`feed.hide`)는 시뮬이 돌 때 숨긴다. 소유자: `xfer{cell,t}`(이송기, 배타) · `belt{cell,line}`(컨베이어 `main`·레인 id) · `amr{id,at}`(적재면 칸).

**부품 AMR 도킹 자리 편집 (M-23).** Admin 「부품 AMR 도크」(`?build=parts`)는 같은 경로 편집 도구(`route-edit.js`)를 부품 루트에 쓴다: `get` = `partsLayout(doc).amr`, `put` 은 SORT 셀만 `layout.amr` 로, 나머지는 `layout.parts` 로 나눠 쓴다(SORT 레인 칸은 두 플릿 공유). 큰 주황 손잡이 = 도킹 자리(창고 PARTS · SORT:IN · 라인 도크). 확정 시 시뮬에 바로 반영되고(부품 ACS 미션을 거두고 충전 자리로 재배치), 경로 점검(두 플릿)과 `dockIssues`(SORT:IN 이 투입 이송기 축 z 에서 0.15 m 넘게 · 라인 도크가 라인 x 에서 0.5 m 넘게 · SORT 레인 x ± 0.3 에 칸 없음) 경고를 로그에 남긴다. 경고만 하고 막지는 않는다. 정규화가 지운 SORT 레인 칸은 다시 끼운다. 서버 저장은 기존 「저장」.

**맞물림 수정 (M-22).** 막다른 도크에서 후진하던 차가 구역 경계(중심 기준)에 서면 차체 0.55 m 가 통로 쪽으로 나와, 그 구역을 잡고 지나가던 차가 개인 간격(반경 합 + 0.1)으로 그 차를 기다리고, 후진 차는 구역을 기다리는 맞물림이 생겼다. `sense` 는 내가 잡은 구역을 기다리며 서 있는 차를 진로(차폭) 밖이면 개인 간격으로 막지 않는다. (출차 전 구역 선점, 3갈래 노드 구역은 시험해 보고 도어트림 소크 교착이 늘어 넣지 않았다.)

## 셀 공정·파지 (`js/sim/parts.js` `process.js` `kin.js` `cellwork.js` `sortwork.js`, M-2~M-12)

**가정.** 공정 순서·시간·작업 지점·부품 치수는 `src/process.default.json`(`assumed: true`)의 가정값이다. 실측·확정 공정이 아니다. 시뮬의 셀 공정은 같은 역할의 JS 모델이고, 실제 셀의 로봇·서보 실시간 제어는 셀 PLC 몫이다. OCS는 수집·감독·재계획만 한다.

**엔티티와 소유자.** 키트·부품마다 소유자가 정확히 하나다: 도어트림 AMR(입고) → 양팔 → SORT 랙 칸 → 양팔 → AMR 적재면 → PRESS·SCREW 하역 로봇 → 스테이션 → (이송 로봇 → 다음 스테이션) → 반출. 부속 토트는 창고 → 부품 AMR → SORT 분류 → 라인 팔레트(`stock`) → 직교이송 → 롤러(`line`) → (비울 때까지) 협동로봇이 상자에서 부품을 집음(`tote`). 흐름 없는 셀은 지그 칸 옮김(4 s)만 한다. 옮김은 `parts.hold(e, 새 소유자, 예상 소유자)`만 쓴다. 예상과 다르면 위반으로 센다. 위치는 소유자에서 계산한다(AMR 위치·로봇 TCP·갠트리 패드·라인 s). 그래서 소유가 바뀌는 순간 위치가 같아야 하고, 테스트가 스텝당 이동 ≤ 0.25 m를 본다.

**작업물(도어트림).** 키트는 도어트림 한 장이다. 모델은 [micro-assembly](https://github.com/theuniversepark/micro-assembly) `assets/blender/doortrim.glb`(Blender 생성 형상, 실물 도면 아님)를 `src/render_asset/doortrim.glb`로 가져왔다. 공정 정의 `kit.model`이 에셋 키, `kit.lay`가 놓임(`upright` 세움 · `face-up` 앞면 위로 눕힘)이다. 기본은 지그에 눕혀 치수 0.8 × 0.16 × 0.565 m(x·높이·z)다. 렌더는 모델을 눕힌 뒤 밑면 중심을 원점에 두고 x·z에 맞춰 균일 배율한다. 모델을 못 읽으면 치수 상자로 그리고 로그에 남긴다. 부품 자리 `at`은 `[dx, dz]` 또는 `[dx, dz, dy]`이고 dy(≤ 0, 키트 윗면 기준)로 트림 면 높이를 맞춘다: P_HDL 손잡이 자리, SW_BEZEL·PW_SW 스위치 패널, Fastener 클립 면. SCREW 부품: BELT_MLDG 벨트라인, SPK_GRL 스피커, INSERT 인서트, CUP_SUB 포켓. 부품 이름은 트림 부위 이름이고 SCREW GLB 라인 이름(A_REST·CUP_SUB·Antenna·UPR)과 맞추지 않았다. 자리·높이는 형상에서 읽은 가정값이다.

**SORT 양팔 입고·적재(가정, M-31·M-33).** 키트는 랙에 생기지 않는다. 도어트림 AMR이 충전 자리에서 원재료를 싣고(5 s, 가정) 랙 뒤 막다른 칸(`SORT:RAW`, 셀 로컬 x 6.36 · z −4.4)에 서면 `unload` 티켓 → 양팔이 적재면 트림을 집어 랙에 놓음. 랙에 놓고 든 뒤(작업 0.88) `released` → AMR은 남쪽으로 후진 출차. 양팔은 하나라 입고와 적재를 동시에 하지 않는다. 분류 키트 적재는 반대편 북쪽 양팔 도크(`AMR_dual_pickup`): 빈 AMR이 서면 `pickup` 티켓 → 양팔이 랙 맨 위 트림 양끝을 같이 잡고 → 대차가 AMR 쪽으로 미끄러지며 몸통이 반 바퀴 돌아 → 적재면에 놓고 든 뒤(작업 0.88) `released` → AMR 출발. 입고·적재 각 12 s. 두 팔은 한 대차(`Dual_arm_slide`)에 앉아 있어 대차 위치 s를 같이 쓰고, 몸통 회전축은 두 팔 베이스 가운데 수직선으로 가정했다(GLB에 허리 관절 없음). 팔마다 관절 보간하면 두 그리퍼 사이가 벌어져서, 매 스텝 키트 중심(몸통 좌표)을 보간하고 두 팔이 IK로 양끝 점을 따라간다(직전 자세에서 시작). 랙은 앞쪽 끝(z −1.22)에 2단이다 — 3단 위 여유 높이와 랙 가운데는 팔이 닿지 않는다. 그래서 SORT 버퍼는 실제로 2다. 랙 트림은 몸통이 돈 만큼 반대로 놓여 있어 AMR에는 셀 기준 yaw 0으로 놓인다(도크에서 AMR이 셀 +x로 서 있다는 가정). 렌더는 팔에 대차·회전을 곱하고 몸통 그룹 `Dual_arm_robot`(이름으로 찾음)도 같이 움직인다. 취소(레이아웃 변경)되면 놓을 때 랙 제자리로 되돌린다.

**하역 핸드셰이크.** AMR이 도크에 서면 `canDrop`(S1 비었고 티켓 없음) → `unload` 티켓 → R6이 적재면에서 키트를 집어 0.15 m 든 순간 `released` → AMR 후진 출차 → R6이 S1에 놓음. 티켓이 없는 미션(공정 정의 없음)은 예전 4 s 고정이다. AMR 라벨은 「PRESS 하역 중」.

**PRESS 흐름(가정).**

| 스테이션 | 단계 (병렬은 ‖) | 시간 |
|---|---|---|
| S1 (지그 서쪽) | 하역 R6 → [R6 L01 P_HDL ‖ R7 L03 SW_BEZEL] | 8 + 11 |
| S2 (지그 가운데) | R9 키트 S1→S2 → [R9 L02 Fastener ‖ R8 L04 PW_SW] → R10 그리스 경로 → R8 검사·반출(동쪽 AMR 적재) | 8 + 11 + 10 + 11 = 40 = takt |

**SCREW 흐름(가정).** PRESS와 같은 엔진·같은 점검이다. 지그 자리 S1 x −0.24, S2 x 1.0(R2·R11 레일 범위 때문에 지그 동쪽 끝 쪽).

| 스테이션 | 단계 (병렬은 ‖) | 시간 |
|---|---|---|

체결은 경로 작업(TCP가 지점들을 지남)이고 나사 엔티티·토크 값은 없다.

`process.js`가 마지막 스테이션 단계 합 = takt = 시나리오 `cycle`, 첫 스테이션 합 + 하역 ≤ takt를 본다. 공급·반출이 충분하면 완료 간격이 PRESS 40.0 s · SCREW 42.0 s다(`tests/process.mjs`). 반출은 빈 AMR 이 도크에 와야 시작하므로, 실제 플랜트 간격은 AMR 배차에 따라 길어진다.

**완료품 반출(가정, M-13~M-15, M-24).** 셀은 완료품을 지우지 않는다. 마지막 단계 `unload`: S2 가 반출 앞 단계에 들어서고 완료품이 있으면 Plant 가 반출 미션을 건다 → 빈 AMR 이 **동쪽 도크**(`PRESS:OUT`·`SCREW:OUT`, 셀 로컬 x +1.83)에 서면 `offerOut` 티켓 → 동쪽 협동로봇(PRESS R8 · SCREW R11)이 S2 에서 집어 AMR 적재면에 놓고 든 뒤(작업 0.85) `released` → AMR 은 들어온 동쪽으로 후진 출차. 11 s. 키트 투입은 서쪽 도크(PRESS R6 · SCREW R1) 그대로. 키 시각은 rig 경로 길이 비율로 정한 고정값이라 rig 유무와 공정 시각이 같다. 레이아웃 변경으로 반출이 취소되면 들고 있던 완료품은 놓을 때 지운다.

**완료품 적재 구역 `OUT`(가정, GLB 없음).** 레이아웃 `sites.OUT`(셀이 아닌 자리, 기본 x −30 · z −2 · PRESS 절반 5.05×5.41 m, SORT 서쪽에 따로. 예전 레이아웃 파일은 기본 자리를 붙여 읽음)과 AMR 지점(북쪽 통로 A4–G4 지선에서 들어와 협동로봇 앞 도크, 후진 출차. 대기는 북쪽 통로 쪽). AMR 이 서면 협동로봇(레일 + 2링크, 가정)이 도어트림을 집어 세워 책장 12칸 중 빈 칸에 꽂는다(14 s, 작업 0.40 `released` → AMR 출발). 칸이 다 차면 8 s 뒤 묶음 출하로 비운다(치움 — 지게차·대차 반출은 그리지 않음). 형상은 절반 크기 셀 프레임 + 뒷벽 책장(작업 칸은 가운데 12). 바닥은 필드와 같은 회색 족. 치수·시간·출하 규칙은 모두 가정이다. 렌더 `outsite.js` 는 절차 형상만 그린다.

**교착 방지.** 동쪽 반출 칸(`PRESS:OUT`·`SCREW:OUT`) 진입 대기는 세로 지선이 아니라 북쪽 통로 쪽(`acs.js` `SPUR_HOLD` 12 m) — 지선에 서면 후진 출차 차를 막는다. SCREW 투입은 충전 자리에서 잠금이 빌 때까지 기다린다(G2 지선이 PRESS:OUT 출차 길). 같은 접속점에 붙는 칸(SCREW·PRESS:OUT)으로는 하역 직후 이어 가지 않고 충전 자리로 빠진 뒤 다시 받는다(`acs.sameHub`). 다른 칸 잠금 차와는 줄로 서지 않고, 잠금 구간에서는 우회하지 않는다(`fleet.js` `yieldTo`). 구역을 잡은 차는 그 구역 밖에 선 차를 막힘으로 보지 않는다. 투입 AMR 은 첫 스테이션이 비고 예약 없는 반출 셀만 예약하고 간다. 받을 셀이 없으면 실은 채 제 충전 자리에서 기다린다(`acs.stage`, 셀 진입 차로를 막지 않게). 투입 운반 대수(실은 채 대기 포함)는 플릿 − 반출 셀 수 이하라 반출 AMR 이 늘 남는다. 플릿이 반출 셀 수 이하면 지금 받을 수 있는 셀 수만큼만 투입한다. 선행 배차 상한(stage)은 SORT 미션만 센다. 같은 4대가 투입·반출을 다 하므로 공급 운반량은 반출 전보다 줄었다(900 s 투입·반출은 배차에 따라 달라진다).

**라인.** 부품 AMR이 라인 도크에 토트 상자를 덤프하면(팔레트 `stock`), 직교이송 2축이 그 상자를 들어 롤러 투입 칸에 내린다(10 s, 투입 칸이 비면 시작). 롤러가 상자를 배출 지점까지 당기면(0.15 m/s, 상자 간격 ≥ 토트 깊이+0.1 m) 협동로봇이 상자에서 부품을 집는다. 토트는 비울 때까지 엔티티로 남는다. 공급이 없으면(무한 재고) 예전처럼 갠트리가 작은 부품을 하나씩 올린다.

**로봇 작업.** 키 프레임(작업 시간 비율): 준비 → 집기 위 → 집기 → 물기(0.30) → 들기 → (투입 작업만: 준비 자세) → 놓기 위 → 놓기 → 압입·풀기(0.80) → 들기 → 준비. 투입은 라인 배출 지점이 로봇 뒤라 반 바퀴 돌아야 해서, 팔을 편 채 돌면 TCP가 너무 빠르고 이웃 구역을 쓸고 지나간다. 그래서 접은 준비 자세를 거치고, 그 시각은 앞뒤 TCP 경로 길이 비율로 나눈다(사건 시각은 그대로). GLB 기구를 붙이면 키 프레임마다 IK 해를 구해(캐시) 관절 공간으로 보간한다. 안 붙이면 작업 지점 사이 직선 보간이다. 공정 시각은 둘이 같다.

**구역 잠금.** 스테이션 남/북 반(S1s·S1n·S2s·S2n)과 도크. 작업 시작에 필요한 구역을 한 번에 잡고 끝에 푼다. 점검: 잠금 없이 구역 작업 높이(키트 + 여유 0.15 m) 안에 들어온 TCP 스텝(`intrude`) = 0. 구역 위를 높이 지나가는 것은 허용한다. 로봇 링크끼리 간섭은 보지 않고 TCP 간격(≥ 0.2 m)만 본다.

**DOWN.** 셀 고장이면 셀 안(로봇·갠트리·롤러·스테이션)이 모두 멈춘다.

**IK (`kin.js`) 한계.** 체인은 형상으로 추정한 5관절 + 레일 직동이다. 위치(3) + 접근 방향(2)만 맞추고 공구 롤은 맞추지 않는다. 관절 가동 범위는 ±π로 두었고 실제 범위·링크 간섭·특이점 회피는 모른다. 해 선택은 직전 자세·준비 자세에 가까운 것(선회축은 싸게). 레일 범위는 이웃 로봇 베이스와의 중간점에서 `railGap`/2 띄운 값이다. 롤러 배출 지점을 베이스 0.73 m 뒤에 두면 최소 도달 거리 안이라 팔을 뒤로 넘기는 해가 나와서, 배출 지점을 롤러 위 z ±2.25로 잡았다. R10은 레일 범위 때문에 키트 북쪽 반에 닿지 않아, 그리스 경로를 Fastener 둘레(남쪽 반)에 두었다.

**렌더(`rigs.js`).** 움직이는 노드(팔 링크·갠트리 가로/승강·롤러 봉)를 셀 그룹 아래 rig 루트로 옮기고(월드 자세 유지) 영점 행렬 M0를 기억한다. 매 프레임 M = P · M0, P는 시뮬과 같은 공간 좌표 POE(레일 이동 · 관절 회전)다. 갠트리 공구 밑에 매달린 대표 부품(GLB)은 숨기고 엔티티를 그린다. 공급 AMR 상자(tote)는 키트 엔티티가 있으면 숨긴다.

**검증.** `tests/kin.mjs`(FK 영점 = TCP, IK 왕복, PRESS 팔 5대 공정 지점 도달) · `tests/parts.mjs` · `tests/process.mjs`(정의 점검, JSON 지점 ↔ GLB 롤러 윗면·갠트리 행정, 사이클 36 s, 소유 위반 0, 순간이동 없음, 잠금 위반 0·구역 진입 0 + 일부러 깬 경우 걸림, 결정론, rig 유무 같은 공정 시각, DOWN 정지, 하역 라벨·출발 순서, 반출: 동쪽 도크·R8/R11 적재·적재면에 놓은 뒤 출발·적재 구역 갠트리가 문 뒤 출발·적재대 칸, 2 h 소크: 10분 창마다 PRESS·SCREW 완료·적재 > 0, 완료 − 적재 ≤ 2, 엔티티 < 100). 화면은 헤드리스 Chrome(`--use-angle=swiftshader`) `?warp=` `?cam=`로 확인.

## 메인 뷰 표현

- **셀 상태.** 발자국 둘레 띠와 바닥 틴트로 보인다. 색은 IDLE 회색, BUSY 초록, DOWN 빨강(점멸)이다. 머리 위 라벨에는 id, 상태, 재고/완료, 진행 막대가 나온다.
- **선택.** 테두리가 굵고 밝아지며 바닥이 펄스한다. 목록이나 3D 클릭으로 고르고, Esc나 빈 곳 클릭으로 해제한다.
- **카메라.** 셀을 고르면 그쪽으로 0.9 s 동안 이동한다. AMR을 고르면 이동한 뒤 따라간다. 사용자가 궤도를 잡으면 이동을 멈추고, 평행 이동 따라가기만 유지한다.

## 테스트

프레임워크 없음. 파일마다 `check(name, ok)` 후 `process.exitCode`. DOM 없는 레이어(`core` `sim` `data`)와 서버를 직접 import 한다. three·DOM 레이어는 브라우저에서 확인.

## 원칙 (meta-factory `docs/DESIGN.md`에서 가져옴)

- 헤드리스 분리(§7-1): 상태·진행은 DOM 없는 모듈. 테스트와 화면이 같은 코드를 돈다.
- 고정 간격(§7-3): 0.1 s 스텝, 배속은 프레임당 스텝 수로.
- 결정론(§7-2): 난수가 들어오면 시드 하나. 표현용 난수는 따로 써서 상태 결과를 바꾸지 않는다.
- 데이터 주도 배치(§7-5): 셀 위치·회전은 코드가 아니라 정의 데이터(`sim/cells.js` 또는 별도 JSON)에 둔다.
- 배치 변경 협의(§7-8): 위치 안·배치도를 먼저 내고 확정 후 반영.
- 닫힌 기본값(§9): 127.0.0.1, 읽기 전용, 비공개. 열 때마다 근거를 남긴다.

완료 기준(§10 축약): `npm test` 전체 PASS · 화면이 바뀌면 브라우저 스크린샷 확인 · 확인한 것과 못 한 것을 나눠 보고.
